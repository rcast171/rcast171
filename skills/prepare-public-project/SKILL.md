# Prepare public project




Follow the user’s approved scope. Preserve unresolved conflicts and report only observed actions and checks. Complete preparation before requesting any necessary review. Existing authorization remains valid; do not request approval again for an already approved action. A completed draft alone is not authorization to publish, install, or send.

1. Define a single audience, problem, useful deliverable and maturity label. Keep related variants together unless users or technical boundaries differ.
2. Inventory code, assets, data, prompts and third-party sources. Verify rights and permissions; do not default to licensing another person's material.
3. Inspect content, exports, metadata and repository history for personal/customer data, confidential strategy and secrets. Create synthetic fixtures where needed.
4. Write a README with problem, actual contribution, demonstration, run/use instructions, evidence, limitations and status. Include an evidence index.
5. Check the links from a signed-out context and verify the included example runs or opens. If source code is unavailable, label it a documented case study.
6. Present the exact prepared package and exclusions. Publish when authorized; otherwise request review of the concrete package.

Required output: Reviewable public package and private exclusions list.

Behavior check: A clean invoice template is reusable; the real customer invoice and supplier pricing remain private. An empty README is not a completed package.
